## IT Sharing 闖關：第 3 關「404 藏 Flag」

> 主題：你以為駭客會先打防火牆？從真實攻擊路徑看企業最容易被入侵的地方
> 本關觀念：**錯誤畫面也可能透露資訊**
> Flag：`flag{2026_IT_Sharing#debugmode03}`

靜態網站放在 [`docs/`](docs/)：

| 檔案 | 用途 |
| --- | --- |
| `docs/index.html` | 虛構的「Oiia 員工自助服務入口」首頁，**沒有任何連到 404 的連結** |
| `docs/404.html` | 任何不存在的路徑都會顯示這頁：上半部是友善的 404，下半部是「忘記關掉的 Debug 輸出」，Flag 就在 Environment 表格最後一列 |
| `docs/vpn-setup.html` | 第 4 關「Base64 解碼」：VPN 安裝說明頁，設定檔裡的「已加密」密碼其實是 Base64 |
| `docs/servicedesk.html` | 第 5 關「HTML 註解」：新版 IT 報修登入頁，原始碼註解裡留著 UAT 測試帳號 |
| `docs/oiia.gif` | 頁首旋轉貓圖示；第 1 關「圖片藏 Flag」：GIF 註解區塊裡藏著 Flag |
| `docs/social.html` | 第 2 關「社群貼文」：虛構社群平台 Purrlink 上 IT 同仁 EricDY 的個人頁 |
| `docs/photos/eric-badge-v3.jpg` | 第 2 關：貼文裡的員工識別證照片（員工編號） |
| `docs/reset.html` | 第 2 關：服務台「密碼重設申請」身分驗證頁，答對顯示 Flag |
| `docs/leave.html` | 干擾頁：首頁「請假與差勤」卡片，顯示系統維護中公告，沒有 Flag |
| `docs/documents.html` | 干擾頁：首頁「文件中心」卡片，文件清單多數需登入；「VPN 用戶端安裝說明」可連到第 4 關 |
| `docs/aitm.html` | 加碼教學頁（非闖關）：中間人釣魚 AiTM 的純動畫示意，無輸入欄位、不收資料，用於揭曉後講解 |
| `docs/.nojekyll` | 讓 GitHub Pages 原樣輸出檔案 |

### 玩法

1. 給聽眾首頁網址（例如 `https://<host>/`）。
2. 首頁的「舊版報修系統（原 /helpdesk 已停止服務）」是提示，但**任何不存在的路徑都可以**，例如 `/helpdesk`、`/admin`、`/test123`。
3. 錯誤頁會把聽眾自己打的網址顯示在 `REQUEST_URI`，下方一路洩漏主機名稱、內網 IP、程式路徑、DB 帳密，最後是 Flag。

### 部署方式

404 頁所有 CSS/JS 都內嵌，不論路徑多深（例如 `/a/b/c`）都能正常顯示。

**GitHub Pages**
Settings → Pages → Source 選 `Deploy from a branch`，Branch 選本分支、資料夾選 `/docs`。GitHub Pages 會自動對不存在的路徑回傳 `404.html`。
（注意：GitHub Pages 上 `/404.html` 本身也能被直接打開，但不影響遊戲。）

**Nginx**（可以把 `/404.html` 設成無法直接存取）

```nginx
server {
    root /var/www/it-sharing/docs;
    index index.html;

    error_page 404 /404.html;
    location = /404.html { internal; }

    location / { try_files $uri $uri/ =404; }
}
```

**Apache**（在 `docs/` 放 `.htaccess` 或寫進 VirtualHost）

```apache
ErrorDocument 404 /404.html
```

### 講者補充（揭曉時可以講的重點）

錯誤頁裡洩漏的資訊（全部都是虛構的）對攻擊者各自有什麼用：

- `APP_ENV=production` 但 `APP_DEBUG=true`：正式環境開著 Debug 模式，這是本關的根本原因。
- `Apache/2.4.29`、`PHP 7.2.24`：版本號可以直接拿去查已知漏洞（CVE）。
- `tpe-portal-web01.corp.oiia.internal`、`10.20.30.15`、`10.20.40.8`：內部主機命名規則與內網網段。
- `/var/www/oiia-portal/...`、`LegacyHelpdeskBridge.php`：程式架構，還透露舊系統的橋接程式仍在運作。
- `DB_PASSWORD`、`LDAP_SERVER`、`SMTP_RELAY`：帳密與內部服務位置，可以直接用來橫向移動。
- `ADMIN_CONTACT`：社交工程與釣魚的目標。

防護建議：正式環境關閉 Debug、使用統一的自訂錯誤頁、隱藏 `Server` / `X-Powered-By` 標頭、機敏設定不要放在環境變數輸出中、定期掃描對外服務的錯誤回應。

## IT Sharing 闖關：第 1 關「圖片藏 Flag」

> 本關觀念：**公開照片也可能留下線索**
> Flag：`flag{2026_IT_Sharing#spinningcat01}`

### 玩法

1. 網站每一頁左上角的旋轉貓 `oiia.gif`，檔案內部的 GIF 註解區塊（Comment Extension）寫著 Flag，畫面上看不到。
2. 讀取方式：
   - 線上 EXIF / metadata 檢視器：下載 `https://2026itsharing.github.io/oiia.gif`，上傳後看 Comment 欄位（手機也可以）
   - 記事本或任何文字編輯器開啟 GIF，`Ctrl+F` 搜尋 `flag`
   - 指令：`exiftool oiia.gif`、`strings oiia.gif | grep flag`、`identify -format '%c' 'oiia.gif[0]'`
3. Windows 檔案內容的「詳細資料」與手機相簿的「資訊」都**看不到** GIF 註解。

技術說明：註解區塊是直接插入原檔，沒有重新壓縮，32 格動畫逐格比對與原圖完全相同。

### 現場提示

- 「這家公司的 logo 圖片裡藏了東西。」
- 「圖片除了畫面，還有什麼？」
- 「把圖片下載下來，用記事本打開看看。」

### 講者補充（揭曉時可以講的重點）

兩種外洩情境：

| | 手機拍照外洩 | 雲端或本地端的圖片原檔外流（本題 DEMO） |
| --- | --- | --- |
| 情境 | 手機拍照直接上傳官網、寄信、貼論壇 | 設計稿、ICON、截圖透過雲端分享連結、Email 附件、官網後台流出 |
| 藏的資訊 | GPS 位置、手機型號、拍攝時間（EXIF） | 作者姓名、編輯軟體與版本、原始檔路徑、註解（XMP、註解區塊） |
| 攻擊者用途 | 找出辦公室或住家位置、推測作息 | 員工姓名、帳號格式、內部資料夾結構、軟體版本 |

- 社群平台（Facebook、Instagram、LINE）上傳時通常會清掉 EXIF；公司官網、Email 附件、雲端分享連結通常保留原檔。
- 會跟著檔案走的是寫在檔案內部的資料（EXIF、XMP、註解）；Windows「內容」裡由檔案系統記錄的資訊不會跟著上傳。
- 防護建議：
  - 對外發布前清除 metadata（Windows「內容 → 詳細資料 → 移除內容和個人資訊」，或 `exiftool -all= 檔名`）。
  - 手機相機關閉「位置標記」。
  - 官網、CMS 上傳流程自動清除 metadata。
  - 照片畫面裡的白板、員工證、螢幕內容同樣會洩漏。

## IT Sharing 闖關：第 2 關「社群貼文藏 Flag」

> 本關觀念：**公開資訊可以拼出工作脈絡**
> Flag：`flag{2026_IT_Sharing#helpdeskreset02}`
> 情境原型：2023 年 MGM 度假村遭駭，攻擊者從 LinkedIn 找到員工資料，打給 IT 服務台冒充員工重設密碼。

### 玩法

1. 首頁頁尾「追蹤我們的員工生活分享：🐾 Purrlink」連到 `social.html`，是資訊部網路組同仁 EricDY 的公開個人頁，貼文由上到下依序出現表單需要的答案。
2. 從貼文拼出三項資料：

   | 欄位 | 答案 | 出處 |
   | --- | --- | --- |
   | AD 帳號 | `ericdy` | 第 1 則（11/20）「指派人請直接選我的 AD 帳號 ericdy」 |
   | 員工編號 | `OI-23087` | 第 2 則（11/16）「到職三週年」，文字與識別證照片都有 |
   | 公司分機 | `1680` | 第 4 則（11/3）「有事打我的公司分機 1680」 |

   第 3 則（11/9）「感謝我們的主管 Jungle 請全組喝飲料」不是答案，重設表單只需要帳號、員工編號、分機三項。

3. 到「新版 IT 報修」登入頁點「忘記密碼？」，進入 `reset.html` 填寫身分驗證。
4. 全部答對會顯示「已為 ericdy 重設密碼」與臨時密碼 `flag{2026_IT_Sharing#helpdeskreset02}`。

技術說明：

- 答案容錯：不分大小寫、忽略前後空白；帳號可帶 `@網域`；員工編號忽略連字號與空白；分機只取數字。
- 首頁最下方「🚩 闖關任務」標示全站共 5 個 flag，格式為 `flag{2026_IT_Sharing#英文關鍵字+題號}`，題號 01～05。
- 答錯會逐欄提示（例如「員工編號與紀錄不符」），方便現場不卡關。
- Flag 用 AES-GCM 加密，金鑰由三個正確答案推導，原始碼裡沒有明文 Flag，也沒有 HTML 註解。
- 社群平台 Purrlink、人物與貼文皆為虛構，不模仿任何真實平台品牌。表單不會送出或儲存任何資料。

### 現場提示

- 「服務台重設密碼要驗證哪些資料？這些資料網路上找得到嗎？」
- 「去看看 EricDY 最近在社群上 PO 了什麼，答案就照表單順序排好了。」

### 講者補充（揭曉時可以講的重點）

- 每則貼文單獨看都很無害，拼在一起就足以冒充本人。
- 攻擊者還能從貼文得知：新報修系統剛上線（可以假冒系統通知釣魚）、週末爬山（社交話題）、識別證長相（可以偽造）。
- 對員工：工作證、螢幕、白板不要入鏡；公開資料不要寫分機、主管、內部系統名稱。
- 對 IT 服務台：身分驗證不能只靠「別人也查得到」的資訊（員工編號、主管、分機），應改成回撥人事系統登記的電話、主管在系統上核准，或使用 MFA 驗證。

## IT Sharing 闖關：第 4 關「Base64 解碼」

> 本關觀念：**編碼不等於加密**
> Flag：`flag{2026_IT_Sharing#notencrypted04}`

### 玩法

1. 首頁「最新公告」的「2026/11/02 VPN 用戶端更新」可以點，連到 `vpn-setup.html`。
2. 步驟 3 的設定檔裡有一行 `password = ZmxhZ3syMDI2X0lUX1NoYXJpbmcjbm90ZW5jcnlwdGVkMDR9   ; 已加密，請安心使用`。
3. 解碼後得到 Flag。
   - 電腦：F12 開 Console，輸入 `atob("ZmxhZ3syMDI2X0lUX1NoYXJpbmcjbm90ZW5jcnlwdGVkMDR9")`
   - 手機：搜尋「Base64 decode」，用任一線上工具

原始碼裡只有 Base64 字串，沒有明文 Flag，也沒有任何 HTML 註解。全站唯一的 HTML 註解在第 5 關的 `servicedesk.html`。

### 現場提示

- 「這個密碼真的有加密嗎？」
- 「結尾的 `=` 是個線索。」

### 講者補充（揭曉時可以講的重點）

- Base64 是**編碼**：規則公開、沒有金鑰，任何人都能還原。**加密**則需要金鑰才能解開。
- 設定檔、腳本、交接文件裡用 Base64「藏」密碼，在 IT 現場很常見，攻擊者拿到檔案等於拿到明文。
- 彩蛋：剛剛把「公司密碼」貼到不知名的線上解碼網站，本身就是一種資料外洩。處理真正的機敏資料要用離線或公司核准的工具。
- 延伸：HTTP Basic 驗證的 `Authorization: Basic ...` 標頭也只是 Base64 的「帳號:密碼」，沒有 HTTPS 就等於明文傳送。
- 設定檔註解寫「共用帳號，請勿外流」：共用帳號本身也是風險，出事時無法追查是誰登入。

## IT Sharing 闖關：第 5 關「HTML 註解」

> 本關觀念：**看不到不等於沒公開**
> Flag：`flag{2026_IT_Sharing#uataccount05}`

### 玩法

1. 首頁的「新版 IT 報修」卡片，或公告「2026/11/16 新版 IT 報修系統正式上線」，都會連到 `servicedesk.html` 登入頁。
2. 畫面上只有登入表單，看不到任何線索。
3. 打開原始碼，表單上方有一段註解：

   ```html
   <!--
     TODO(上線前移除)：UAT 測試帳號，給廠商驗收用
     帳號：helpdesk.test
     密碼：flag{2026_IT_Sharing#uataccount05}
   -->
   ```

4. 用這組帳密登入，會顯示「登入成功：歡迎，helpdesk.test（UAT 測試帳號）」，示範攻擊者拿到帳密後直接使用。

查看原始碼的方式：

- 電腦：右鍵 →「檢視網頁原始碼」或 `Ctrl+U`（Mac：`⌘+Option+U`），或 F12 → Elements
- Android Chrome：網址前加 `view-source:`，例如 `view-source:https://2026itsharing.github.io/servicedesk.html`
- iPhone Safari：沒有內建檢視原始碼，請改用電腦或和旁邊的人一起看

技術說明：

- 登入頁只在瀏覽器端用 SHA-256 雜湊比對，原始碼裡只有雜湊值，明文 Flag 只出現在註解裡。
- 表單不會送出任何資料，也不會儲存；頁面上註明這是虛構網站，請勿輸入真實帳密。
- 報修頁故意不叫 `/helpdesk`，讓第 3 關的提示路徑仍然是 404。

### 現場提示

- 「畫面上看到的，就是網頁的全部嗎？」
- 「在網頁上按右鍵看看。」

### 講者補充（揭曉時可以講的重點）

- HTML 註解不會顯示在畫面上，但整份原始碼都已經下載到使用者的電腦裡。
- 攻擊者不會一行行看，而是用工具自動抓網站原始碼，搜尋 `password`、`TODO`、`admin`、`api` 這類關鍵字。剛剛用 `Ctrl+F` 搜尋 flag 的人，做的就是同一件事。
- 只要送到前端的東西都等於公開：HTML 註解、隱藏欄位、用 CSS 藏起來的元素、JavaScript 檔案。
- 防護建議：
  - 正式環境打包時自動移除註解（前端 minify 工具都有這個選項）。
  - 給開發者看的說明改用伺服器端註解，例如 PHP 的 `//`、ASP.NET 的 `<%-- --%>`，不會送到瀏覽器。
  - 帳號密碼不該出現在前端程式碼，搭配程式碼審查與 Secret Scanning 把關。
  - 測試帳號上線前停用，並設定到期日。

## 首頁計分卡

首頁最下方「🚩 闖關任務」區塊內建個人計分卡：

0. 區塊說明提醒：解題時除非逼不得已，請盡量不要使用 AI 工具，親手操作才能體會駭客的攻擊手法。
1. 輸入暱稱後開始闖關，可隨時「更改」暱稱，分數保留。
2. 輸入 flag 後提交：答對顯示「#3 答對！+20 分」，重複提交顯示「已經解過了」，答錯顯示「flag 不正確」。
3. 配分：#1 15 分、#2 20 分、#3 20 分、#4 20 分、#5 25 分，滿分 100；滿分會顯示恭喜訊息。
   計分卡上的題名刻意不透露解法，並附一句暗示：

   | 題號 | 題名 | 暗示 |
   | --- | --- | --- |
   | #1 | 旋轉的秘密 | 那隻一直轉的貓，好像知道些什麼。 |
   | #2 | 熱心的同事 | 有位同事什麼都愛 PO，連不該 PO 的也 PO 了。 |
   | #3 | 迷路的網址 | 走錯路的時候，網站好像說了太多話。 |
   | #4 | 安心的密碼 | 說是加密了，真的嗎？ |
   | #5 | 看不見的備忘 | 畫面上看到的，不一定是全部。 |
4. 「重新開始」會清除暱稱與分數。

技術說明：

- 分數只存在各自瀏覽器的 localStorage，換裝置、無痕模式或清除瀏覽器資料就會消失；沒有全場排行榜。
- 原始碼只存 5 個 flag 的 SHA-256 雜湊，看不到明文 flag；比對前會做全形轉半形、去空白、不分大小寫。
- 沒有新增 HTML 註解，全站唯一的註解仍在第 5 關。
- 彩蛋：檢查都在瀏覽器端，懂技術的人可以直接改 localStorage 拿滿分。揭曉時可以帶出「前端驗證不等於安全」。

## 加碼教學：中間人釣魚（AiTM）

`docs/aitm.html` 是五題之外的教學頁，首頁闖關任務區塊底部有連結，也可由講者直接給網址 `/aitm.html`。

- **純動畫示意**：按「播放示範」會逐步演出一次 AiTM 攻擊（員工 → 攻擊者代理 → 真 SSO），並即時標出攻擊者側錄到的帳密、MFA、session cookie。
- **不是闖關題、沒有 Flag**。
- **安全性**：頁面沒有任何 `<input>`／`<form>`，不會接收、傳送或儲存任何資料；演示用的帳密與 cookie 皆為假字串，動畫全在瀏覽器端跑，無任何網路請求。
- **核心觀念**：AiTM 偷的是登入後的 session cookie，不是密碼，所以簡訊／推播型 MFA 擋不住。防護：改用防釣魚 MFA（FIDO2 / Passkey / 硬體金鑰）、條件式存取、核對網址。
- **真實案例**：2022 年起微軟多次公開報告大規模 AiTM 釣魚竊取 Microsoft 365 session，後續接商業郵件詐騙（BEC）。
